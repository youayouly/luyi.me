# GitHub Console 本地项目控制台

GitHub Console 是一个面向作者自己日常开发流的本地控制台：把多个仓库的启动入口、运行状态、预览跳转和说明文档统一收在同一页里，让“先开哪些项目、当前谁在跑、该去哪里看”这些重复动作不再分散在多个终端和目录之间。

它不是线上 SaaS，也不是替你操作 GitHub 权限、分支或发布的自动平台。它更像一个偏本机的工作台，把高频启动和观察动作集中起来，同时保留人工确认这条边界。

## 1. 要解决什么问题

当一个人的日常工作同时跨 `page`、`news`、`RAG Abroad` 等多个仓库时，真正消耗注意力的往往不是“怎么写代码”，而是这些零碎动作：

- 记住每个项目的端口、命令和入口地址。
- 频繁切目录，再重复敲同一批启动命令。
- 打开浏览器后还要重新找对应页面或预览入口。
- 想确认某个服务有没有真的跑起来时，又得回终端或系统进程里翻。

如果这些步骤都留在命令行里，熟练度一旦中断，重新进入状态的成本就会很高。GitHub Console 的目标不是替代终端，而是把“进入工作状态前的准备动作”压缩成一个可视化入口。

## 2. 核心体验

这个控制台把多项目管理拆成几种最常用的动作，并尽量让它们在一个页面里闭环：

| 模块 | 作用 |
| --- | --- |
| 项目概览卡片 | 用统一卡片显示项目名、运行状态、入口地址和操作按钮 |
| 一键启动 | 把勾选的项目批量启动，减少逐个切目录执行 |
| 项目开关 | 控制某个项目是否参与当前控制台管理 |
| 预览跳转 | 直接打开项目当前预览，不再自己记端口 |
| 事件流 | 记录刷新、保存配置、启动结果，方便回看最近动作 |
| 文档说明 | 把命令、进程与说明信息集中放到同一视图 |

它刻意保留“人工点击”这一步，而不是把所有能力都做成自动后台动作。因为这里处理的是本地多仓库环境，作者更需要的是一个可靠的控制面，而不是一个悄悄替你做决定的黑盒。

## 3. 架构与实现

GitHub Console 的实现很轻：一个本地 Node hub、几张静态页面和一组 PowerShell 启动脚本。

```text
PowerShell 启动脚本
    ↓
Node 本地 hub（端口、进程、状态、项目操作）
    ↓
docs 静态页面（卡片、文档说明、事件流）
    ↓
联动 page / news / RAG Abroad 等本机项目
```

**Node 本地 hub** 负责读取项目配置、探测端口和进程、提供状态接口，并把项目启动/停止动作收口成统一 API。

**静态页面层** 负责把这些状态转成更容易扫描的界面：哪些项目正在运行、哪些被加入一键启动、当前有哪些预览可以直接打开。

**PowerShell 脚本层** 则继续承担本机启动职责，让“从网页发起动作”和“从命令行快速开工”保持一致，而不是维护两套完全不同的入口。

## 4. 产品取舍

- **本机优先，不追求公网化**：这是个人工作流控制台，不需要伪装成面向所有人的在线服务。
- **集中入口，不接管 GitHub**：它能整理项目和状态，但不会越界去做分支权限、push 或发布审批。
- **保留人工确认**：适合本地高频操作的才做快捷入口，高风险动作继续交给人工判断。
- **统一观察面，而非重型编排系统**：重点是“我现在该开什么、去哪看、发生了什么”，不是把本机开发环境做成复杂运维平台。
